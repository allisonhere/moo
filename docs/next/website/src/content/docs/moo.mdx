Moo is a terminal workspace for coding agents. It combines detachable sessions, agent detection, provider integrations, handoffs, teams, and a socket API. Its own binary, configuration, state, and sockets keep installations separate.

:::note
Moo is experimental. Tagged GitHub releases are available; supported workflows and platform validation are still developing. Install only revisions or releases you trust.
:::

## Requirements

- A Rust toolchain compatible with the repository. Use the `rust-toolchain`/`Cargo.lock` versions the checkout expects.
- [Zig](https://ziglang.org/download/) 0.16.0 for the vendored libghostty-vt terminal core. Put `zig` on your `PATH`, or set `ZIG=/path/to/zig` before building.
- A terminal emulator with normal ANSI and mouse support. Moo is a TUI, so it needs a real terminal.
- Linux is the primary development target. macOS and Windows build paths exist, but Moo is not yet validated on every platform.

## Build and install

### Release install

From the repository root:

```sh
./scripts/install-moo.sh
```

The script builds the locked release target with `cargo build --release --locked --bin moo` and installs `moo` to `~/.local/bin` by default. Set `MOO_INSTALL_DIR` to choose another binary directory. The script does not edit your shell configuration.

Make sure the install directory is on your `PATH`, then start it:

```sh
moo
```

### Run from the checkout

For development, run the debug binary directly:

```sh
cargo run --bin moo
```

or, after a build:

```sh
./target/debug/moo
```

Debug builds use the `moo-dev` directories, so they do not share state with a release install.

## Run

Start the TUI where you want to work:

```sh
moo
```

The first launch creates a config file and onboarding state. Detach with `prefix+q` (the default prefix is `ctrl+b`) and reattach with `moo`.

Useful commands:

```sh
moo --version
moo --help
moo --default-config
moo status server --json
moo workspace list
```

## Runtime paths

Moo uses the `moo` binary and `MOO_*` environment variables. Release and debug builds keep separate configuration and state:

| | Moo release | Moo debug |
| --- | --- | --- |
| Binary | `moo` | `moo` |
| Config | `~/.config/moo` | `~/.config/moo-dev` |
| State and logs | `~/.local/state/moo` | `~/.local/state/moo-dev` |
| Default sockets | under the config directory | under the config directory |

The socket file names are `moo.sock` and `moo-client.sock` inside Moo's own config directory. Agents, plugins, and integrations that moo launches receive the `MOO_*` variables.

Moo tags panes it launches with `MOO_PRODUCT_ID=moo`. If it inherits a socket from a managed pane belonging to another product, it refuses to reuse that socket instead of attaching to an incompatible server.

## Features

### Command palette

Press `prefix+space` to open the command palette. Type to filter with fuzzy matching, use Up/Down or `j/k` to move, Enter to run the highlighted action, and Esc to close. Built-in actions show their keybindings, and the palette also lists commands advertised by the server, plugins, and popups. The narrow-terminal switcher exposes the same commands in a scrollable menu.

### Teams

`moo teams ui` opens a keyboard-first screen for Teams, creating the session's store (an owner credential and a durable event log) the first time (`moo teams init` does that step on its own): a navigator (All teams, then Projects, Teams and Agents), a workspace with Terminals, Chat, Tasks and Decisions views, and an inspector for the selected team or agent. On Linux and macOS the command palette always lists **teams: open screen**, **teams: decisions** and **teams: new team**, each opening the screen in a pane over the current tab; close it with `q` to go back. The workspace views (Terminals, Chat, Tasks, Decisions) are folder-style tabs with a rounded top, and the open one joins the workspace below it (`1` to `4` switch).

The screen adapts to the terminal: three areas from 100 columns, the side areas collapsing (`n` and `i` dock them) at 61 to 99, and one area at a time (Tab to switch) at 60 and below. `:` opens its own command palette with the commands that apply to what is selected, `?` lists the keys, `D` switches density, `A` uses ASCII glyphs, `H` makes focus high-contrast and `t` previews the built-in themes. It follows your configured theme.

- **Decisions** shows approvals and conflicts. `a`, `d`, `v` and `x` open a confirmation with the exact scope before anything is sent, and only the Owner can decide. Text typed in chat is never an approval.
- **Chat** messages start with `@lead`, `@dev`, `@qa` or `@agent-id` to address a role or one agent. The audience is sent as a field and enforced by the server, so scoped messages are readable only by the sender, the addressee and the Owner.
- **Providers and models** (`P`, Owner only) declares the AI providers and models you use, prefers one per role (`p`) and gives a team's role one (`e`). It records your declaration and never checks it.
- **Terminals**: `b` records which Moo pane runs an agent (and which provider), and Enter on a bound agent focuses that pane. Teams records the link; it does not start agents.
- **New team** (`:` then *new team*) edits a draft, shows a review screen, and only then creates the credentials, the team spec and the team. *Propose a team from a goal* fills the same draft: the server runs the program named by `MOO_TEAMS_PROPOSER` in its own environment (goal on stdin, a JSON draft on stdout), or returns a plain template named from the goal. The screen only edits the draft; checking and creating the team are server methods any client can call, documented in the [Teams API](/docs/teams-api/).

Teams commands work for local sessions only. [Teams](/docs/teams/) explains how it all fits together: plans, providers, what agents are told, disagreements, costs and limits, recovery and upgrading.

### Agent names in the sidebar

The lower-left agents panel shows the agent name you assigned, then integration-provided display metadata, then the detected agent kind.

To rename an agent:

- Right-click its row in the agents panel and choose **Rename agent**, or **Clear agent name** to remove the override.
- Press `prefix+shift+a` to rename the focused agent. The default binding is configurable as `keys.rename_agent`; set it to `""` to disable it.
- Use the CLI from another terminal:

```sh
moo agent rename <target> <name>
moo agent rename <target> --clear
```

Targets accept a unique live agent name or the pane ID that currently hosts the agent. Names must start with a lowercase letter and contain only lowercase letters, digits, `-`, or `_`, up to 32 characters.

A user-assigned name takes precedence over integration-provided display labels, and it is used on the pane border as well. Clearing the name falls back to the integration label or the detected agent kind.

### Agent handoff

Open the command palette and choose **agent handoff** to forward one agent's recent output to another. The entry appears when at least two agents exist.

Pick the source in the **from** column and the target in the **to** column. Use Up/Down or `j/k` to move, Tab or Left/Right to switch columns, Enter to send, and Esc to close. Clicking a row selects it.

Moo reads the source's last 40 lines and submits them to the target as a prompt, exactly like `moo agent handoff <from> <to>`. The server's normal checks still apply, so a blocked or busy target rejects the prompt and the modal stays open to retry.

### Plugin actions in Settings

Open **Settings** and choose **plugins** to list the actions of every linked plugin that the server's host can run, for example `Start Ovis`, `Stop Ovis` and `Turn Ovis autostart off`. Select an action and press Enter (or click **run**) to invoke it, the same as `moo plugin action invoke`. The status line shows that the action started; it does not show the action's output, so use `moo plugin log list` for that.

The left pane moves between sections with Up/Down or `j/k`. Press Right, `l` or Enter to move into a section's choices, and Left or `h` to return. Tab and Shift-Tab cycle sections from either pane.

### Web UI through the Ovis plugin

The [Ovis](https://github.com/devswha/ovis) browser and phone client runs as a moo plugin: a chat view of each agent's transcript, approval cards, a live terminal and push alerts, served on `127.0.0.1:7317`. Use the [Moo-compatible branch](https://github.com/allisonhere/ovis/tree/moo). Link a checkout of it with `moo plugin link <checkout>` and start it with `moo plugin action invoke devswha.ovis.start`; moo's startup hook then starts it with each server. Ovis stops with the server: about 15 seconds after `moo server stop` (or a crash) it shuts itself down, and a quick stop and start leaves it running; set `OVIS_STOP_WITH_MOO=0` to keep it running without a server. Turn autostart off with `moo plugin action invoke devswha.ovis.autostart-off`. Who can open it is a setting: **Settings → Phone & devices → Network access** in the app chooses *This PC only* (the default) or *Local network*, which answers only this PC and private addresses and refuses everything else. It needs `OVIS_TOKEN` or a paired device first. The same switch is the plugin actions `network-local` and `network-lan`. Anonymous usage counts are off unless you set `OVIS_TELEMETRY=1`. Setup, safety notes and known issues are on the [wiki](https://github.com/allisonhere/moo/wiki/Web-UI-with-Ovis).

### Remote machines

Remote attach and saved SSH machines discover `moo` on the remote host.

- For a same-platform POSIX remote, Moo installs the local Moo binary when the remote copy is missing or older.
- Set `MOO_REMOTE_BINARY` to an explicit Moo binary or package to override the install source.
- Windows remote installation requires an explicit Moo package; automatic installation is refused.
- SSH authentication and host-key checks use the configured SSH client.

## Update

To update from source, pull a reviewed Moo revision and run the install script again. For a binary install, rerun the [Linux installer](/docs/install/):

```sh
git pull
./scripts/install-moo.sh
```

`moo update` explains the update process without downloading a binary.

## Release process

Maintainers release from a clean, pushed `master` checkout:

```sh
./deploy.sh
```

The full-screen release console shows repository readiness and the release pipeline. Choose a patch, minor, or major bump, toggle dry-run mode if needed, then run **Validate**, **Commit**, **Push**, and **Tag & release** in order. **Commit** includes tracked changes and the Cargo version bump. Untracked scratch files are shown but ignored.

For scripting, pass `patch`, `minor`, `major`, or an explicit version such as `1.2.3` directly. `./deploy.sh --dry-run patch` validates the source and shows the selected version without changing files, commits, or tags.

The script updates the Cargo package version, runs `just check`, commits the version files, and pushes an annotated tag. The Moo release workflow builds Linux, macOS, and Windows assets, includes the Windows ConPTY runtime, writes `SHA256SUMS`, and publishes the GitHub release.

## Remove

Delete the `moo` binary. Its config and state remain until you explicitly remove the `moo` or `moo-dev` directories:

```sh
rm -f ~/.local/bin/moo
rm -rf ~/.config/moo ~/.local/state/moo
```

These commands remove only Moo’s release data. Debug-build data lives in the separate `moo-dev` directories.

## Troubleshooting

### `zig executable not found`

Install Zig 0.16.0 and put it on `PATH`, or point the build at it:

```sh
ZIG=/path/to/zig cargo build --release --locked --bin moo
```

### `refusing to use a Moo socket inherited from another product`

You launched Moo inside a managed pane belonging to another product, such as Herdr. Start it from a normal terminal instead. If you intentionally want to bypass the inherited socket, clear the relevant variables:

```sh
env -u MOO_ENV -u MOO_PRODUCT_ID \
    -u MOO_SOCKET_PATH -u MOO_CLIENT_SOCKET_PATH \
    moo
```

### Nested moo is blocked

Starting moo inside another moo session prints `nested moo is disabled by default`. Run outside the other session, or opt in explicitly in the Moo config:

```toml
[experimental]
allow_nested = true
```

### `moo: command not found`

Add the install directory to your `PATH`, for example `~/.local/bin`.

### Remote setup or Windows attach fails

Set `MOO_REMOTE_BINARY` to a compatible Moo binary or package for the target machine. Windows remote installs are not available without an explicit package.

### Logs

Find the server log in Moo's config directory, for example `~/.config/moo/moo-server.log`.

## Development

Use the repository recipes:

```sh
export ZIG=/path/to/zig
just test
just check
```

`just test` runs the Rust suite plus the repository contract tests. `just check` also runs formatting and the broader checks. The full toolchain expects `just`, `cargo-nextest`, and `bun`; the Windows cross-lint additionally needs `just setup-windows-cross` once to download the Microsoft SDK.

Moo adds no telemetry or required cloud account. Network use includes configured agent providers and remote machines, optional remote agent-detection manifest checks, and explicitly requested downloads such as plugins and installer updates.

## Current limitations

- The name **Moo** is temporary while product branding is undecided.
- Linux release downloads are available through the Moo installer. Self-update is disabled; rerun the installer to update. POSIX remotes seed the local Moo binary; Windows remotes need an explicit package.
- The larger agent workspace features are still in progress: a unified agent dashboard and multi-agent orchestration are not part of this build. Agent status history is available through `moo agent history` and the **session replay** palette entry.
