The Teams API is the source of truth for Teams. The Teams screen (`moo teams ui`) is one client of it and holds no orchestration logic of its own: anything it does, another program can do with the same methods and the same credentials. This page is the reference; the machine-readable form is `moo teams schema` (also `teams.schema.v1`, and checked in at `docs/next/api/teams-api.schema.json`).

## Transport and authentication

- The API is reached through the local Moo API socket, the same socket as the rest of the JSON API. It is **local only**: there is no network listener (see [Remote access](#remote-access)).
- One request, one response: write a single JSON object and a newline, read a single JSON line back, close.
- Request: `{"id": "<1-128 bytes>", "method": "teams.list.v1", "auth": {"bearer": "<token>"}, "params": {...}}`. `auth` is omitted for the two open methods.
- Success: `{"id": ..., "result": {"type": "...", ...}}`. Error: `{"id": ..., "error": {"code", "message", "retryable", "retry_after_ms"?, "details"?}}`.
- A token is the 64 hex characters in a credential file. Credential files must be private (mode `0600` in a `0700` directory); the server and `moo teams` both refuse a loose one. Create the Owner's with `moo teams init` and others with `moo teams keygen PATH`, or let `teams.drafts.launch.v1` create a team's three. Tokens are never put in request files, argv or logs.
- Authority comes from the credential, never from message text. Chat messages are data: nothing typed in chat approves, assigns or launches anything.

## Versioning and compatibility

- `api_version` is `1` and changes only on a break. `api_minor` rises when methods or optional fields are added; each method lists the minor that introduced it (`since_minor`).
- Discover what a server supports with `teams.capabilities.v1` (open, no credential): `methods`, `method_catalog`, `operations`, `errors`, `limits`. A method that is not advertised is not available, and calling it returns `unknown_method` without disconnecting anything else. A client should disable only the feature that needs it.
- Method names end in `.v1`. A method's meaning and the fields it returns never change: new response fields are additive, new request fields are optional with a documented default, and anything that would change behavior gets a new method name. Clients must ignore response fields they do not know. Requests refuse unknown fields so a typo is an error.
- Frozen fixtures in `tests/fixtures/teams-api-v1/` record the response keys and the request set of API 1.0 clients; the test suite replays them against the current server. Do not edit them to bless a change.
- This API is separate from the TUI client endpoint (generation 1). Nothing here changes those codecs.

## Operations

Every change is one **command** sent in `teams.mutate.v1`: `{"expected_revision": N, "idempotency_key": "...", "command": {"kind": "...", ...}}`. The same command can be dry-run with `teams.validate.v1`. The authority class says who may send it: *agent* (an agent acts inside its own scope), *lead* (a Lead directs bounded work) or *owner* (only the Owner). The server rechecks authorization when the command runs. `teams.capabilities.v1` carries the same table with a sample of every command.

### Team drafts, proposals, launch, pause and resume

A team is built from a **draft**: a name, a project (empty means the default project), and ids for the Lead, Developer and QA. Three Owner-only methods handle it, so a script, the Teams screen and a person at a terminal do exactly the same thing:

1. `teams.drafts.propose.v1 {"goal": "..."}` returns a draft. With no proposer configured the draft is a plain template named from the goal (`"source": "template"`). The operator can set `MOO_TEAMS_PROPOSER` in the **server's** environment to a program that reads the goal on stdin and prints `{"name": ..., "lead": ..., "developer": ..., "qa": ...}`; the request cannot choose or change that command. A proposal is only ever a suggestion.
2. `teams.drafts.validate.v1 {"draft": {...}}` says whether the draft is valid (`problems` lists why not), which team id it would get and where its credential files would go. Nothing is created.
3. `teams.drafts.launch.v1 {"expected_revision", "idempotency_key", "draft"}` creates the three private credential files and the team in one all-or-nothing commit, and returns their paths. Replaying the same key returns the same result and creates nothing twice.

`suspend_team`, `resume_team` and `cancel_team` pause, continue and stop a team; a suspended team cannot start or advance work, and attaching or detaching a client never suspends anything.

### Plans, providers, memory, disputes and limits (API 1.3)

These arrived in API 1.3. Older clients keep working: nothing in 1.0 to 1.2 changed, and a client that never calls these methods never sees them.

**Providers and plans.** The snapshot lists `providers`, `preferences` and `role_assignments`. The Owner declares providers with `declare_provider` (the Teams screen's `P` does the same): an id, a label, the capabilities it says it has, its models, how it meters usage (`metered`, `estimated` or `none`) and whether the integration can stop spending at a limit. Teams does not check any of it; every provider reads `verified: false`, and that never changes. `propose_plan {plan_id, goal}` turns a goal into a draft plan: a team draft, tasks with dependencies, any specialists the goal justifies, a provider for each role, and a list of `explanations`, each with the words of the goal that caused it. The planner is a fixed keyword table with no model and no randomness, so the same goal and the same declared providers give the same plan. `edit_plan` changes it before launch with ops: `rename_team`, `set_project`, `add_task`, `remove_task`, `restore_task`, `set_task_title`, `set_task_dependencies`, `drop_recruitment`, `restore_recruitment`, `set_role_provider`. `teams.plans.launch.v1 {expected_revision, idempotency_key, plan_id}` creates the team, its credentials and its tasks in one commit. Specialists come back as `pending_specialists`: the Lead requests them with `request_recruitment` after the task they are listed for, and nothing starts on its own.

**Changing a role's provider mid-run.** `reassign_role_provider` is a Lead command, and it spends an Owner approval for exactly that change (a `rights_escalation` on `<team>:<role>` carrying the provider and model). Without a matching approval it is refused. Before launch, the Owner uses `assign_role_provider` or `edit_plan` instead.

**Memory.** `teams.memory.retrieve.v1 {team_id?, task_id?, budget_bytes?}` returns what an agent should be told, within a byte budget (8 KiB by default, 32 KiB at most): accepted requirements and ADRs, the task, the latest handoff with its exact evidence, review decisions, and current context notes. Every item carries `provenance` (what it came from and at which revision), and items are included whole or not at all. Chat, scoped messages and transcripts are never included. A note made with `put_context_note` must name between one and eight sources and a validity window; once a source changes, the note is listed in `excluded_as_stale` with the reason instead of being served. The answer is a view at `as_of_revision`, not a standing instruction: fetch again when the revision moves. Requirements and ADRs start as `proposed`; `accept_knowledge` makes them visible to agents and `supersede_knowledge` replaces one.

**Disputes.** `raise_dispute` needs a topic and at least two distinct pieces of conflicting evidence. At most two peers answer with `respond_dispute`, so a dispute has three positions at most. The Lead closes an ordinary dispute with `resolve_dispute`. A dispute marked `architectural`, or one where peer review has run its course without settling it, goes to the Owner (`escalated`) and only `decide_dispute` closes it. A question already decided cannot be reopened without new evidence (`dispute_settled`), and a team has at most 6 open disputes.

**Usage and limits.** `report_usage` is the Owner's harness telling Teams what a provider consumed. Only a provider declared `metered` can report cost as metered; everything else is an estimate. Snapshots show the two apart: `reliable` (from metered providers) and `estimated` (approximations, never enforced, never to be read as a bill), plus `warnings`, which say so when a provider has no spend cap or no metering. `set_team_limits` sets a ceiling on metered cost and tokens; once reached, new work is refused with `usage_limit_reached` until the Owner raises it. Work in flight is capped too (see Limits).

**Agent state.** `set_agent_state` puts a team's Lead, Developer or QA in `idle` (takes no new work), `released` (also revokes its credential and removes its pane binding) or back to `active`. A Lead controls only their own team and cannot bring a released agent back; an agent cannot idle or release itself.

**Summary.** `teams.summary.v1 {stuck_after_seconds?}` lists, per project and team, approvals waiting, escalated disputes, agent states, usage and stuck tasks. A task counts as stuck when it has not changed for 30 minutes unless you say otherwise, and each stuck task carries `suggested_actions`, for example `retry_dispatch` for a failed dispatch. Teams only suggests; it never retries anything for you.

## Reading chat, tasks, approvals and decisions

`teams.messages.list.v1`, `teams.tasks.list.v1`, `teams.approvals.list.v1` and `teams.decisions.list.v1` take `{"team_id"?, "task_id"?, "status"?, "cursor"?, "limit"?}` and return `{"items", "has_more", "next_cursor", "revision", "stream_id", "watermark"}`.

- `limit` is 1 to 100 (default 50). Pass the previous `next_cursor` as `cursor`; stop when `has_more` is false.
- Messages and decisions are immutable and ordered by `(revision, id)`, the order they happened. Tasks and approvals change over time, so they are ordered by `id`. A cursor names the last item returned by a key that never changes, so a page never repeats or skips an item because something changed in between.
- A cursor the server did not issue is `invalid_cursor`. `status` filters on the record's status tag, for example `pending` for approvals.

A message has an `audience`: `{"to": "team"}` (the default), `{"to": "role", "role": "lead"|"developer"|"qa"}` or `{"to": "actor", "actor_id": "..."}`. The audience is a field the server enforces; a leading `@lead` in a client's text box is only that client's way of choosing it.

## Events and replay

Every committed change appends events to one durable, ordered log per store.

- **Ordering model.** Events have a `sequence`, a gapless, strictly increasing integer. The log belongs to a `stream_id`, fixed for the life of the store and unchanged by restarts. `(stream_id, sequence)` is a cursor. Each event carries `prev_hash` and `hash`, a chain over the log, and the `authority` class and server time (`at`) the change ran under.
- **Reading.** `teams.events.list.v1 {"stream_id", "after", "limit"}` returns events with `sequence > after` (up to 100), `next_after` (use it as the next `after`), `has_more`, and `watermark` (the newest sequence). Only events the caller may read are returned, but `next_after` still advances past the ones they may not, so skipped events cause no loop. `teams.events.resume.v1` is the same call under a name that says what it is for.
- **Watching.** `teams.events.wait.v1` takes the same parameters plus `timeout_ms` and holds the request open until there is an event the caller may read, or the wait ends with an empty page. Waits are capped at 25 seconds, at 4 open per credential and 64 overall (`too_many_subscriptions` with `retry_after_ms`); `timeout_ms: 0` polls. Waiting never blocks writers.
- **Backpressure.** The server keeps nothing per subscriber. A slow reader just asks for the next page when it is ready; a reader that falls too far behind gets `cursor_expired`.
- **Retention and cursor expiry.** The log keeps at most 4000 events; past that the oldest are compacted away down to 2000, and the chain stays verifiable. A cursor older than the retained log, from another stream, or from the future returns `cursor_expired` with `details`: `stream_id`, `retained_from` (the first sequence still held) and `watermark`.
- **Recovering.** A client that missed events, lost its connection, or got `cursor_expired` does this: read `teams.snapshot.get.v1`, take its `stream_id` and `last_event_sequence` (the watermark), replace its picture of the world with the snapshot, and resume with `after = watermark`. The snapshot is taken at or after the watermark, so nothing after it is lost; re-delivered events are idempotent by `sequence`. After a server restart the same cursor stays valid.

## Writes

- **Revision check.** `expected_revision` must equal the store's current `revision` (from any snapshot or mutation result). Otherwise `revision_conflict`: read a snapshot and retry with a fresh key.
- **Idempotency.** `idempotency_key` (1-128 bytes) is scoped to the caller. Repeating a request with the same key and command returns the original result and applies nothing again; the same key with a different command is `idempotency_conflict`. Receipts are kept for the newest 4000 writes. Use a fresh random key per intended change and the same key when retrying after a lost reply.
- **Atomicity.** A command, or a draft launch, commits all of its changes and events or none.

## Limits

- Requests are rate limited per credential: 20 writes/s (burst 60) and 50 reads/s (burst 200). Failed authentications share one small bucket (5/s, burst 20), so guessing a credential is slow and cannot starve real users. A refusal is `rate_limited` with `retry_after_ms`: wait that long.
- Work in flight, per team, is capped. These are hard limits, not advice: 3 tasks in progress (`concurrency_limit`), 40 open tasks, 20 queued dispatches, dependency chains 6 deep (`task_depth_limit`), 3 dispatch attempts per task (`retry_exhausted`), 6 open disputes. A plan has at most 12 tasks and 4 specialists, and a project at most 16 providers. `teams.capabilities.v1` reports all of them under `work_limits`.
- A message body is at most 16 KiB; a page at most 100 items; the store at most 10000 records and 16 MiB.

## Privacy

| Reader | Team chat | Role message | Direct message | Events about them |
|---|---|---|---|---|
| Owner | all | all | all | all |
| Sender | yes | yes | yes | yes |
| The addressed role or agent | yes | yes | yes | yes |
| Others on the same team | yes | no | no | no |
| Another team | no | no | no | no |
| A recruited specialist | no | no | no | none (sees its own engagement only) |

A teammate who may not read a scoped message cannot learn from the event stream that it exists. Teams only see their own tasks, approvals, worktrees and integrations; cross-team conflicts and notices are shared with the two teams they name. Project knowledge is shared with the project's teams; team knowledge stays private. `teams.audit.list.v1` (Owner only) lists recent refused requests.

## Examples

With the `moo teams call` command (credentials are given with `--credential-file`, never inside the request):

```sh
moo teams init                                   # prints the owner credential file
echo '{"id":"1","method":"teams.list.v1","params":{}}' > req.json
moo teams call req.json --credential-file ~/.config/moo-dev/teams-owner.key

moo teams schema > teams-api.schema.json         # this build's machine-readable schema
```

The sample client in `examples/teams-client/teams_client.py` uses only the Python standard library and shares no code with Moo:

```sh
K=~/.config/moo-dev/teams-owner.key
teams_client.py --credential-file $K list-teams
teams_client.py --credential-file $K read-chat --team alpha
teams_client.py --credential-file $K send-message --team alpha --to qa "ready for review?"
teams_client.py --credential-file $K watch-status           # survives restarts and expired cursors
teams_client.py --credential-file $K submit-approval ap-1 --approve --reason "reviewed"
```

`submit-approval` works only with the Owner's credential; with any other it prints `refused: forbidden` and exits 1. `watch-status` prints events as they arrive, honors `retry_after_ms`, reconnects after a restart, and resyncs from a snapshot on `cursor_expired`.

## Security checklist

- [x] The API is reachable only through the local socket; there is no network listener and `teams.capabilities.v1` reports `"network_gateway": false`.
- [x] Every method but discovery and the schema needs a credential; credential files must be private regular files, and tokens are never logged, audited or echoed in errors.
- [x] Authority is checked on the server, per command, at the moment it runs. No chat, list or event method can approve, deny or revoke anything.
- [x] Approvals can be decided only by the Owner, bind the exact action by digest, expire, and are single use.
- [x] Scoped messages are filtered when read and when events are delivered; another team and a specialist see nothing of them.
- [x] Writes are idempotent and revision-checked; drafts launch atomically.
- [x] Requests are rate limited per credential, failed authentications share a small bucket, event waits are bounded, and nothing is queued per subscriber.
- [x] Refused requests (bad credential, forbidden, rate limits, spent or expired approvals) are recorded in a private, bounded audit log; accepted changes are in the hash-chained event log.
- [x] The goal proposer is a program named by the operator in the server's environment; a request supplies only the goal text, which is length-limited.
- [ ] **Not enforced:** agents run as ordinary processes. A shell running as the same OS user can read credential files, edit the store directly or run git, so keep the Owner's credential out of agents' reach. The API enforces its rules for callers that use it; it does not sandbox anything. See *Limitations*.

## Remote access

There is deliberately no HTTP, SSE or WebSocket gateway in this release. The raw Moo local control socket must never be exposed, and a gateway that reaches a store holding approval authority needs authentication, scope-based authorization, binding restrictions and protection against browser-origin attacks that cannot be demonstrated here. Until it can be, use the API from the same machine (or over SSH to a shell on it). A future gateway is a design constraint, not a promise: it would be opt-in, listen on nothing by default, bind to loopback or a Tailscale interface only, require a token with scopes (read, chat, approve), reject requests with a browser `Origin` it did not allow, and translate each request to the same `teams.*` methods so there is one implementation.

## Limitations

- Local only; one request per connection; no push channel other than `teams.events.wait.v1`.
- Every command revalidates the whole state, so cost grows with the store (limited to 10000 records).
- Teams records worktrees, merges and approvals; it does not run git, start agents, or sandbox them.
